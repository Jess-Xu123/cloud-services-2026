Application Description

This application is a full-stack web system converted from Docker Compose to a CSC Rahti (OpenShift/Kubernetes) cloud environment.

Architecture Overview:
  • Frontend: Nginx static web server serving this documentation and an interactive Todo List application, accessible publicly via a TLS Route.
  • Backend: Python Flask API isolated within the internal cluster network, using Redis to cache task lists and Unsplash to fetch task images.
  • Database: MySQL server configured with a PersistentVolumeClaim (PVC) to guarantee persistent data storage.

Data Operations: Tasks are stored in MySQL, task lists are cached in Redis, and new tasks can include an image from Unsplash.

QUESTION 1

Explain the difference between SAML and OAuth. When would a company chose one over the other?

SAML(Security Assertion Markup Language): is a technology that lets you log in just once at a central system (the identity provider) to securely access multiple apps (Service Providers) without re-entering password. It is like showing ID once at a park entrance to get a wristband, which then lets people onto all the rides (Fortinet, 2026).

SAML focuses more on Authentication, and the data formatted is with XML. SAML assertion contains authentication and authorization data. The user is authenticated by an identity provider vis SAML assertion, and authorization is granted to access services.

OAuth(Open Authorization) is a standard that lets a third-party app access specific data on your behalf (like your contacts or profile photo) without giving it your password. It is like giving a housekeeper a temporary keycard that only unlocks the front door, rather than handing over the master keys(Fortinet, 2026).

OAuth primarily focuses on authorization, the data format is JSON. And the user is authorized via access token, but identity is not authenticated because the authentication is separated using OpenID Connect (Fortinet, 2026).

A company chooses SAML when it needs a centralized login system for its employees to access all workplace applications (like HR portals or company email) securely through a wev browser using a single password.

The company can choose OAuth when it needs to build mobile apps, open up AOIs, or let different software services safely share specific user data without sharing passwords (like allowing a calendar app to view your Google Calendar).

QUESTION 2

What is YAML and why has it become the default configuration format for Kubernetes/Rahti manifests? Compare it briefly to JSON.

1.The concept of YAML

"YAML stands for YAML Ain't Markup Language. It is a data serialization format. A way of representing structured data as text that human can read and write without too much pain." (Narayan, R. 2026)

YAML is a human-friendly format used to write configuration files. It used simple text and indentation(spaces) to organize data. It is like a clean digital shopping list or outline.

Kubernetes files are written, read, and maintained by humans. YAML is chosen because it is clean, easy to read and supports comments, making complex cloud configurations much easier for people to manage and review (Narayan, R. 2026).

Like aforementioned, YAML is built for human readability. It removes syntax like curly braces {} and square brackets []. It used spaces to define data hierarchy and supports comments, making it easy for engineers to write, edit, and document configuration files.

JSON is built for fast machine processing. it strictly enforces brackets {} [], quotes "", and commas,, while completely ignoring whitespace. And it doesn't support comments, making long configuration files harder for humans to read and maintain.

QUESTION 3

Describe one real or hypothetical use case for blockchain in supply-chain or IoT tracking (see "Yes, These Chickens Are on the Blockchain"), and evaluate whether blockchain was actually necessary for it.

Use case

A real-world use case is tracking free-range chickens in China (Gogo Chicken by LianAn Technology). Each chicken wears an IoT smart leg band that records its steps, location, and daily activity. This tracking data is saved onto a blockchain so consumers can scan a QR code at the market to verify the chicken's origin, history, and organic status.

I think the blockchain was not necessary in this case. Blockchain is a decentralized, digital ledger that securely stores data and transactions across a network of computers.

Although blockchain makes the saved data tamper-proof, it can't verify if the data entered at the start is true. If someone puts the smart leg band on a caged chicken or transfer the band to a different chicken, the blockchain will faithfully record false information. A traditional centralized database maintained by a trusted third-party auditor would achieve the exact same operation tracking at a much lower cost. Blockchain here servers mostly as a marketing tool to build consumer trust rather than a strict technical necessity.

Step 1: Review the Week 5 Changes

The application keeps MySQL as the persistent data store, uses Redis as a short-lived cache, and calls the Unsplash API from the backend when a task is created.

You can see the full code from my git repo - week-5.

  • backend/app.py: fetches task images from Unsplash, stores their URLs in MySQL, caches todo reads in Redis, and invalidates the cache after a successful insert.
  • backend/requirements.txt: lists the Flask, MySQL, Redis, and HTTP client dependencies.
  • db/init/init.sql: defines the todos table, including the image_url column, for local Docker Compose initialization.
  • frontend/index.html: renders todo images and reports API errors.
  • rahti/configmap.yaml, rahti/redis-deployment.yaml, and rahti/redis-service.yaml: configure the Redis service and backend connection.

Step 4: Update the Todo Database Table

The MySQL Deployment uses a PVC and does not automatically run the local db/init/init.sql file in Rahti. Create the table after MySQL is ready. If the table already exists, check for image_url and run the ALTER TABLE statement only when that column is missing. 

oc exec -it deployment/db -- mysql -u appuser -p appdb
CREATE TABLE IF NOT EXISTS todos (
  id INT AUTO_INCREMENT PRIMARY KEY,
  task VARCHAR(255) NOT NULL,
  image_url VARCHAR(1024) NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

SHOW COLUMNS FROM todos LIKE 'image_url';

If SHOW COLUMNS returns no row, run this migration once. Do not run it when the column already exists.

ALTER TABLE todos ADD COLUMN image_url VARCHAR(1024) NULL;
