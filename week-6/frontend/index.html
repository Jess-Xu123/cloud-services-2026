Week 6 Assignment

Application Description

This application is a full-stack web system converted from Docker Compose to a CSC Rahti (OpenShift/Kubernetes) cloud environment.

Architecture Overview:
  • Frontend: Nginx static web server serving this documentation and an interactive Todo List application, accessible publicly via a TLS Route.
  • Backend: Python Flask API isolated within the internal cluster network, using Redis to cache task lists and Unsplash to fetch task images.
  • Database: MySQL server configured with a PersistentVolumeClaim (PVC) to guarantee persistent data storage.
CI/CD & Observability
  • Automated Deployment: Integrated with a GitHub Actions CI/CD pipeline that automatically builds, pushes container images on code changes, and updates the application on CSC Rahti via OpenShift CLI.
  • Health & Reliability: Configured with Kubernetes Liveness and Readiness Probes to ensure self-healing and zero-downtime availability.
  • Monitoring & Logs: Enhanced with structured logging (tracking request paths and response times) accessible via cluster logs, alongside dedicated dependency health check endpoints.

Data Operations: Tasks are stored in MySQL, task lists are cached in Redis, and new tasks can include an image from Unsplash.

QUESTION 1

Explain the difference between Continuous Integration, Continuous Delivery and Continuous Deployment.

Continuous Integration: refers to the practice of automatically and frequently integrating code changes into a shared source code repository and automatically built and tested (Red Hat, 2025).

The CI pipeline is triggered when a developer pushes code or creates a pull request. It builds the application and runs automated tests to detect integration problems early. The goal of CI is to make sure new code can be safely integrated with the existing code.

Imagining this as building Lego together with friends. Every time a friend finishes a small block, they bring it to the main table and connect it to the shared model. An automatic machine checks whether the new block fits and whether it breaks anything that has already been built.

Continuous Delivery: after passing CI, the application is automatically prepared and kept ready for release, but a human needs to decide when to deploy it to production (Alex M., 2026).

After the test passes, the application is automatically packaged and deployed to a staging or other pre-production environment. The application is kept in a release-ready state, but a human still decides when to deploy it to production.

Continuous Deployment: in practice means automating the releases of a developer's changes from the repository to production, where it is usable by customers (Red Hat, 2025).

Continuous deployment refers to fully automated release. If code passes all automated tests, it goes live to end users immediately. The main difference between Continuous Delivery and Continuous Deployment is whether human intervention is required before production deployment.

QUESTION 2

Describe the structure of a GitHub Actions workflow (triggers, jobs, steps). What would a minimal pipeline for the app you built in Week 4/5 need to do?

A GitHub Action workflow is an automated process defined in a .yml file inside the .github/workflows directory.

Triggers: events that instruct GitHub Actions when to execute the workflow. Common triggers include code pushe, pull_request or schedule.

Jobs: define what the workflow will actually execute. A single workflow can contain one or multiple jobs running either in parallel or sequentially depending on dependencies.

Steps: individual tasks executed sequentially within a single job. A step can either run shell commands/scripts or execute reusable pre-built components known as Actions.

My week 5 application is an To-Do App with Redis cache and Unsplash Public API. A minimal CI pipeline for this application would be:

  • Trigger: automatically start when I push code to the main branch
  • Checkout code: retrieve the repository source code using actions/checkout@v4
  • Set up runtime environment: initialize the required runtime(Python) on the virtual runner.
  • Provision Redis container: spin up a temporary, lightweight Redis service container (using image redis:7-alpine, exposed on port 6379) so the test suite can interact with a live cache instance.
  • Inject secrets: pass the Unsplash API key as an environment variable sourced securely from secrets.UNSPLASH_API_KEY.
  • Install dependencies: run the package manager installation command.
  • Execute tests: run automated tests to verify core CURD operations, Redis caching read/write behavior, and Unsplash API integration.

What is alert fatigue, and how would you design a small set of alerts for a student project that avoids it?

“Alert fatigue is a state of mental and operational exhaustion caused by an overwhelming number of alerts—many of which are low priority, false positives or otherwise non-actionable (Krantz & Jonker, 2025).”

When engineers receive so many alerts that they start to ignore them.

My application is rather small, so I need to create alerts only if it requires immediate human intervention:

Backend service down
- Condition: the backend API fails health check request for 2 consecutive minutes.
- The application is completely unusable for users, immediate service restart is necessary.
Redis database disconnection
- Condition: the backend fails to read/write to the redis cache cluster for more than 5 consecutive times.
- Redis is a primary data dependency; losing the cache degrades performance or crashes state handling..
Unsplash API failure
- Condition: external requests to the Unsplash API show an error rate over 50% in a 5-minute window.
- key feature of this application is not functional and requires credential or fallback checking.

QUESTION 4

Why should secrets (registry tokens, cluster login tokens) never be hard-coded into a CI/CD pipeline file? How does GitHub Actions handle this instead?

Hard-coded secrets into CI/CD pipeline can experience security risks

  1. Public and internal exposure: vision control systems like GitHub track the entire history of a repository. Once a credential is committed, it remains exposed in the commit history even if deleted later. Anyone with read access to the repository can extract it.
  2. Unauthorized access & compromise: exploited registry tokens allow attackers to delete or inject malicious code into application container images. Compromised cluster login tokens grant full or partial administrative control over deployment infrastructure, potentially leading to data breaches, service hijacking, or unauthorized resource consumption (Ejiofor, J., 2026).

GitHub Actions helps prevent these risks by using encrypted secrets

  • Centralized and encrypted storage: secrets are stored outside the repository in Settings -> Secrets and variables -> Actions. The secret values are encrypted and can't be viewed as plain text after they are saved.
  • Dynamic variable injection: instead of writing sensitive information directly in the .yml file, developers can use ${{ secrets.SECRET_NAME }} to access the stored secret during the workflow.
  • Runtime masking: when the workflow runs, GitHub Actions hides secret values in the logs. If a secret is printed in the logs, it is shown as *** instead of the actual value.
  • Ejiofor, J. (2026, February 18). Secrets management failures in CI/CD pipelines. DevOps.com. https://devops.com/secrets-management-failures-in-ci-cd-pipelines/

Step 3: Deploy MySQL and Redis

Apply the persistent storage, database, and Redis resources. The Redis container runs as a cache without RDB/AOF disk persistence because the Rahti container filesystem is not writable for Redis snapshots; todo data remains persistent in MySQL.

oc apply -f rahti/mysql-pvc.yaml
oc apply -f rahti/mysql-deployment.yaml
oc apply -f rahti/mysql-service.yaml
oc apply -f rahti/redis-deployment.yaml
oc apply -f rahti/redis-service.yaml

oc get pvc
oc get pods
oc get services

Wait until the MySQL and Redis pods show Running and Ready before continuing.

Step 4: Update the Todo Database Table

The MySQL Deployment uses a PVC and does not automatically run the local db/init/init.sql file in Rahti. Create the table after MySQL is ready. If the table already exists, check for image_url and run the ALTER TABLE statement only when that column is missing. 

oc exec -it deployment/db -- mysql -u appuser -p appdb
CREATE TABLE IF NOT EXISTS todos (
  id INT AUTO_INCREMENT PRIMARY KEY,
  task VARCHAR(255) NOT NULL,
  image_url VARCHAR(1024) NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

SHOW COLUMNS FROM todos LIKE 'image_url';

If SHOW COLUMNS returns no row, run this migration once. Do not run it when the column already exists.

ALTER TABLE todos ADD COLUMN image_url VARCHAR(1024) NULL;
Step 5: Build and Push Updated Images

Build for linux/amd64 so the images run on Rahti. Use a new version tag whenever you publish code changes. These are the versions used for this deployment.

docker login

docker build --platform linux/amd64 -t jessxu123/lempbackend:1.0.3 -f backend/Dockerfile .
docker push jessxu123/lempbackend:1.0.3

docker build --platform linux/amd64 -t jessxu123/lempfrontend:1.0.5 -f frontend/Dockerfile .
docker push jessxu123/lempfrontend:1.0.5

Docker Hub must contain both repositories, and the logged-in account must have permission to push to them. The image tags in the Deployment manifests must match the tags pushed here.

Step 6: Apply Manifests and Wait for Rollouts

Set the image tags in rahti/backend-deployment.yaml and rahti/frontend-deployment.yaml to the versions pushed above, then apply the manifests. Applying a changed image starts a new rollout. 

oc apply -f rahti/configmap.yaml
oc apply -f rahti/redis-deployment.yaml
oc apply -f rahti/redis-service.yaml
oc apply -f rahti/backend-deployment.yaml
oc apply -f rahti/backend-service.yaml
oc apply -f rahti/frontend-deployment.yaml
oc apply -f rahti/frontend-service.yaml

oc rollout status deployment/cache
oc rollout status deployment/backend-deployment
oc rollout status deployment/frontend-deployment
oc get pods

For a later code update, build and push a new image tag, change the matching image: value in the Deployment YAML, and apply that file again.

Step 7: Create the Public Route and Test the App

Create the public HTTPS route if it does not already exist, then test the health endpoint, task list, and task creation.

oc get route frontend || oc create route edge frontend \
  --service=frontend-service --insecure-policy=Redirect
oc get route frontend

APP_URL="https://$(oc get route frontend -o jsonpath='{.spec.host}')"
curl -i "$APP_URL/api/health"
curl -i "$APP_URL/api/todos"
curl -i -X POST "$APP_URL/api/todos" \
  -H 'Content-Type: application/json' \
  --data '{"task":"Week 5 verification"}'

A successful health check returns 200; creating a task returns 201. Reload the page to confirm the task and its Unsplash image appear. To inspect the running application, use oc logs deployment/backend-deployment and oc logs deployment/cache.
