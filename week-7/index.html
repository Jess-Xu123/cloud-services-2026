QUESTION 1

What is Infrastructure as Code, and which problems of manually created infrastructure does it solve? Use your own Week 1 VM setup as an example.

Infrastructure as Code: is a way of managing infrastructure such as networks, virtual machines, and load balancers using configuration files instead of manually configuring them (Hewlett Packard Enterprise, n.d.).

Instead of clicking around in a web dashboard to set up a server, configure a network, and attach storage by hand, IaC provides a way to replace manual configuration with configuration files.

Based on my Week 1 VM setup, I think IaC solves the human error and inconsistency problem. I needed to manually set up the virtual machine and server on C-Pouta. If I missed a checkbox or misconfigured a security group, or mistyped an IP address, it could lead to severe downtime or security breaches.

IaC can help me automate the infrastructure setup so that the same configuration can be applied every time without manual typos or inconsistent settings.

Beside the human error and inconsistency issue, manual configuration also makes version control and auditability more difficult.

When I manually setup the virtual machine and server, it is difficult to track when and why a setting was changed. Reverting a bad configuration change also requires manual troubleshooting. With IaC, the configuration files can be stored in Git, making changes easier to track, review, and revert.

QUESTION 2

Explain the difference between declarative and imperative infrastructure automation. What does idempotency mean, and why is it important?

Declarative: defines the desired end state of the infrastructure rather than execution steps. You specify what the final result should look like in configuration files. The tool automatically compares the code with the real-world state and makes only the necessary changes to reach that end state.

Imperative: defines the exact sequence of steps required to achieve a configuration (e.g., shell scripts or CLI commands). You must instruct the machine step-by-step. If an error occurs midway, the process halts, leaving the infrastructure in an incomplete or inconsistent state.

Idempotency: means that executing the same operation multiple times yields the exact same final result as executing it once, without causing extra side effects.

In infrastructure management, network timeouts or deployment failures are common. An idempotent tool (OpenTofu or Terraform) allows you to safely re-run the deployment command without creating duplicate resources or breaking existing ones.

QUESTION 3

Why was OpenTofu created? Compare Terraform and OpenTofu — would the choice between them matter to you as a developer, or to a company?

OpenTofu and Terraform are both infrastructure-as-code tools. They use the same configuration language (HCL), the same state format, and the same providers. Therefore, the main differences are their licensing, governance, and roadmap direction.

OpenTofu was created because HashiCorp changed Terraform's license from the open-source Mozilla public License (MPL 2.0) to the restricted Business Source License (BSL) in August 2023 (Azhybaeva, 2026).

OpenTofu was created as a free, open-source alternative and donated to the Linux Foundation to ensure vendor neutrality and prevent single-company control. It also guarantees a project roadmap driven by community needs rather than corporate profit (Azhybaeva, 2026).

As a developer: I don't think the choice matters much for learning the basic IaC concepts, because both tools use HCL and have very similar workflows. The skills are also transferable: knowing how to use one makes it easier to learn the other.

As a company: it would matter because:

  1. Licensing risk: companies worry about future licensing shifts or compliance violations under non-standard open-source terms like BSL.
  2. Ecosystem requirements: companies deeply embedded in HashiCorp Cloud Platform services may prefer Terraform, while greenfield projects or companies with strict open-source requirements may prefer OpenTofu.

QUESTION 4

What is the state file used for? Why should it not be committed to a Git repository, and how do teams usually share it instead?

The state file *.tfstate.* and *.tfstate serves as a single source of truth mapping the IaC configuration code to real-world cloud resources. It tracks resource IDs, configurations, and metadata so OpenTofu knows what has already been created, modified, or needs to be deleted.

Image if we are building an office building, main.tf is the main architectural blueprint and cloud.yaml is the access pass and credentials that grant OpenTofu permission to enter and operate within the cloud infrastructure. terraform.tfstate is the asset inventory record. It maps each component in the blueprint to the actual physical resources created in the cloud. When you add a new room to the design, OpenTofu references this inventory to know exactly what already exists, enabling it to apply only the necessary changes rather than rebuilding from scratch.

The *.tfstate.backup file is automatically generated as a fallback copy before any state modification.

It shouldn't be committed to a Git repository because (Wagh, 2022):

  1. security risks: state files store sensitive data in plain text, such as passwords, private keys and environment variables. Committing them to Git exposes credentials to unauthorized users.
  2. State corruption and race conditions: If multiple team members commit different version of the local state file to Git, it creates merge conflicts and corrupts the infrastructure's tracking record.

Teams use a remote backend such as S3-compatible object storage like CSC Allas to store the state file centrally. Remote backends support state locking, which prevents simultaneous executions from messing up the infrastructure state while ensuring every team member works against the exact same up-to-date record.

4. Reflection: Manual vs. Code

Aspect Manual setup (Week 1) Infrastructure as Code (IaC)
Effort Creating each setup required dozens of clicks in the web interface. It was time-consuming and easy to miss a security rule or configuration option. Writing the code and troubleshooting it takes time initially, but each subsequent deployment can be completed in seconds.
Repeatability It is difficult to ensure that two servers have exactly the same configuration, making human error likely. The same code can be applied repeatedly to produce consistent baseline infrastructure across environments.
Security Overly permissive security group rules can be left behind, such as allowing SSH access from 0.0.0.0/0. Security rules are defined in code, with validation such as restricting access to a single IP in CIDR notation. Git also provides an audit trail for configuration changes.
Applicability Best suited to temporary, quick tests or prototype validation. Suitable for production, replicating development, test, and production environments, and disaster recovery.

5. Problems Encountered & Solutions

Problem 1

cloud-init scripts may fail to run correctly when Windows and Mac line endings are incompatible.

Solution

In the user_data attribute in main.tf, I used replace(..., "\r\n", "\n") to normalize line endings.

Problem 2

There is a risk of exposing sensitive credentials in terraform.tfvars or other configuration files.

Solution

I created a .gitignore file at the start of the project to exclude *.tfvars, clouds.yaml, and state files such as *.tfstate from Git version control.
