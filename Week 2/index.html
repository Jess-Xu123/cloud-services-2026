Question 1

Compare application containers to microservices

Answer:

"Containerized applications are applications run in isolated packages of code called containers." (Google Cloud, n.d.)

A container is like a small, independent box. It puts the software code and everything it needs into one place. Considering it as a lunch box, it has the food (the application) and all the utensils (the dependencies) needed to eat it. You can take this lunch box anywhere.

"Microservices is an architecture where an application is divided into small, independent services that communicate over a network. Each service handles a specific function and can be developed and deployed separately." (GeeksforGeeks, 2026)

Microservices is like a food market where each vendor specializes in one type of food. Similarly, each microservice specializes in one specific function.

The main difference lies in their focus:

Microservices represent an architectural design that breaks a large application into smaller business functional units, whereas application containers are a packaging and deployment technology. In practice, they complement each other—containers are the ideal lightweight environments used to host, deploy, and scale individual microservices independently.

In the IT industry, companies like Amazon combine them in practice (Aumann & Banelis, 2023):

1. Business Splitting (Microservices): Architects divide a complex e-commerce system into dozens of independent microservices (e.g., user profile, shopping cart, payment). Each service is built and managed by a small dedicated team.

2. Packaging & Isolation (Containers): Developers use tools like Docker to package each microservice and its dependencies into a container image. This guarantees that code runs identically on a developer's local Mac and on cloud production servers like AWS or Google Cloud.

3. Auto-scaling (Kubernetes): During high-traffic events like Black Friday, container orchestration tools(Kubernetes) automatically scale up the specific microservice container (e.g., payment service) from 2 to 200 instances to handle the spike, and scale back down when traffic normalizes to save costs.

Question 2

Explain what is serverless architecture?

Answer:

"Serverless architecture is a cloud computing model where the cloud provider manages the underlying infrastructure, including servers, storage, and networking. Developers can focus on writing and deploying application code."(GeeksforGeeks, 2026)

Serverless doesn't mean there are no servers literally, it means that the developers don't need to manage the servers.

Legacy server (traditional server) is like owning a car, no matter you drive to work or not, you have to pay for the insurance, maintenance, and other associated costs.

Serverless architecture is like using a Uber or Bolt, you don't need to worry about the maintenance. Only when you need to go somewhere, you pay for the ride. Otherwise, you don't have to pay anything.

In IT industry practices:

1. Event-Driven Execution: Code runs only when triggered by specific user requests or system events (e.g., uploading an image or clicking a button).

2. Pay-per-Use Billing: Unlike traditional cloud servers that charge a continuous monthly fee for idle time, serverless charges strictly for the exact millisecond duration that the code executes.

3. Automatic Scaling and Zero Operations: The cloud system instantly scales from zero to thousands of concurrent executions during high-traffic spikes without requiring manual infrastructure setup or operating system maintenance.

However, serverless also has some limitations (Patten, 2024):

  • Higher costs at large scale: for high-volume workloads, the pay-per-use model can become significantly more expensive than running dedicated servers or containerized applications (Dave Patten, 2024). Imagine it is cheap when you occasionally use Uber/Bolt to go somewhere. But if you have a delivery company, the bill will be much bigger.
  • Cold starts & performance latency: If a function hasn't been used for a while, the cloud provider needs time to wake it up, which can cause delays for end-users.

Question 3

List some information security risks when using third party (for example Docker) containers?

Answer:

Using third-party containers introduces critical software and infrastructure security risks if they are not verified or configured properly. According to Chainguard (2025), key security risks include:

1. Known Vulnerabilities in the Base Image: Third-party container images downloaded from public repositories often contain outdated system packages or unpatched software libraries with known common vulnerabilities and exposures. Attackers can easily use the flaws to break into the application.

2. Hidden Malicious Code: unsafe containers can carry hidden bad scripts, such as bitcoin miners that steal your computer's power, or backdoors that give attackers full remote control.

3. Leaked Passwords and Dangerous Configurations: Container creators often accidentally leave secret keys or passwords inside the container files. Also, sharing sensitive host folder access with a container gives attackers a direct key to control the background Docker system.

4. Too Much Authority (Container Escape): If a container is given high administrative access (like the --privileged flag), an attacker inside the container can break out of its sandbox and control your entire computer system.

Question 4

List some benefits of IaC (Infrastructure as Code) for modern software development

Answer:

"Infrastructure as Code (IaC) is a practice of transforming infrastructure blueprints into executable code." (Port, n.d.) Instead of manually setting up cloud resources through a graphical user interface, infrastructure can be managed using code files, acting like a master blueprint that automates setup.

Key benefits of IaC for modern software development include:

1. Speed and Automation: Development teams can automatically provision and destroy complete infrastructure in minutes rather than days by running automation scripts.

2. Consistency and Reduce Human Error: By removing manual configuration steps, IaC guarantees that environments are created identically, eliminating configuration drift and human mistakes.

3. Version Control and Traceability: Since infrastructure is written as code, it can be tracked, audited, and reviewed using version control tools like Git, enabling instant rollbacks if a failure occurs.

4. Cost Efficiency and Optimization: Cloud resources can be dynamically created only when needed and destroyed immediately when idle (such as shutting down test environments overnight), significantly reducing operational costs.

Company Example:

Company like Netflix heavily rely on IaC tools (e.g., Terraform) to automatically manage, scale, and deploy thousands of servers globally on AWS to serve millions of streaming users without manual intervention.
