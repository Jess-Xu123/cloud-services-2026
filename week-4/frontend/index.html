Application Description

This application is a 3-container full-stack web application converted from Docker Compose to a CSC Rahti (OpenShift/Kubernetes) deployment.

Architecture Overview:

  • Frontend: Nginx static web page presenting this documentation and an interactive Todo List application. It is publicly exposed to the Internet via a Rahti TLS Route.
  • Backend: Node.js/API communicating strictly through the internal Rahti cluster network. It interacts with the database.
  • Database: MySQL server running with a PersistentVolumeClaim (PVC) to guarantee data persistence.

Data Operations: The application demonstrates continuous Read operations (fetching the existing Todo list from MySQL) and Write operations (adding new Todo items and saving them permanently into MySQL).

Explanation & Comparison

1. ConfigMaps vs. Secrets

Both ConfigMaps and Secrets are used to separate configuration artifacts from container image content, keep applications portable and modular.

ConfigMap: Designed to store non-sensitive, plain-text configuration data (such as database hostnames, port numbers, environment flags, or configuration files like nginx.conf).

Secret: Designed specifically to store sensitive data (such as database passwords, API keys, SSH keys, and TLS certificates).

2. Database Persistence Mechanism

A PersistentVolumeClaim (PVC) in Rahti/OpenShift represents an abstract request for durable cloud block storage. Unlike a Docker Compose local volume—which stores data directly on a single host machine's local disk—a PVC binds to an independent, network-attached Persistent Volume (PV).

  • Resilience: If a physical host in Rahti fails, OpenShift reschedules the MySQL Pod onto another healthy node and automatically re-binds the existing PVC, ensuring zero data loss.
  • Decoupled Lifecycle: PVC in Rahti exists independently of the Pod lifecycle. Even if the MySQL Pod is manually deleted (oc delete pod), the PVC retains all database records safely in the cloud storage layer.

Rahti PVC: is similar like saving a file to Google drive. The data doesn't belong to a physical machine. If the machine breaks, one can simply login from another device, connecting to PVC, and all files are immediately loaded where you left them.

Docker Compose Local Volume: is more like saving files to a USB drive plugged into a laptop. It works great on your machine, but if your laptop breaks or you move to a server across the world, that local flash drive isn't accessible to other machines.

3. Pod Recovery & Orchestration

Self-Healing: When a backend Pod is manually deleted using oc delete pod, Kubernetes/OpenShift doesn't leave the system in a broken state. Instead, it immediately detects that a Pod has disappeared and automatically schedules and spawns a brand-new Pod to replace it.

4. Service Discovery & Load Balancing

In OpenShift/Kubernetes, Pod IP addresses are temporary and change every time a Pod restarts, scales, or gets recreated.

Instead of connecting directly to an individual Pod's IP address, the frontend sends requests to a fixed Service name (e.g., http://backend-service:8000).

The Service acts as a single, permanent virtual entry point that automatically keeps track of all active backend Pod IPs (Service Discovery) and evenly distributes incoming HTTP traffic across them (Load Balancing).

5. Problems & Solutions
01
CPU architecture mismatch

The images built on an Apple Silicon Mac used the ARM64 architecture, but Rahti requires Linux AMD64 images. Rahti could not find a compatible image.

Solution: The backend and frontend images were rebuilt with --platform linux/amd64 and pushed to Docker Hub again.

02
Incorrect backend Service name

The first frontend image configured Nginx to proxy requests to backend, but the Kubernetes Service was named backend-service. Nginx failed with a "host not found in upstream" error.

Solution: The Nginx upstream was changed to backend-service:8000, using the internal Kubernetes Service DNS.

03
OpenShift non-root restrictions

Rahti runs containers with a non-root user. Nginx could not write to its default cache directories or bind to privileged port 80, causing the frontend Pod to enter CrashLoopBackOff.

Solution: Nginx temporary files and its PID file were moved to /tmp. Nginx now listens on port 8080, and the Deployment and Service use that container port.

6. Comparison: Rahti vs. Docker Compose + cPouta

Deployment:

cPouta requires manual provisioning of a virtual machine, installing Docker, and running docker compose up. Rahti utilizes declarative OpenShift/Kubernetes manifests (oc apply -f), allowing developers to deploy applications without managing underlying VMs or OS environments.

Networking:

Docker Compose relies on local bridge networks and static host port mappings on a single machine. Rahti abstracts network routing through Services (for internal DNS service discovery and load balancing) and Routes (for secure external HTTP/HTTPS access across cluster nodes).

Maintenance & Operations:

On cPouta, scaling, container recovery, and OS patches require manual sysadmin work. Rahti provides automated self-healing, rolling updates (RollingUpdate), dynamic resource management, and decoupled cloud storage (PVC), drastically reducing operational overhead while ensuring high availability.
